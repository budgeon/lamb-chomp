# Native Verification

Unit tests and gates prove rules and data. This pass proves the app builds, launches, and plays on an iOS Simulator at real screen sizes.

## One-time setup (user)

- Xcode with an iOS Simulator runtime: `xcode-select -p`, `xcrun simctl list runtimes`.
- Java is required by Maestro: `java -version` (17+). Homebrew's `openjdk@17` is keg-only, so system `java` does not find it unless you run the `sudo ln -sfn …` step from its caveats. Without that step, Maestro works only when `JAVA_HOME=/opt/homebrew/opt/openjdk@17` is set.
- Maestro: `brew tap mobile-dev-inc/tap && brew install mobile-dev-inc/tap/maestro`, or `curl -fsSL "https://get.maestro.mobile.dev" | bash`. Check with `maestro --version`.

If any of these is missing, Verify is `BLOCKED`. Ask the user; do not try to work around it.

## Environment preflight (orchestrator, at Setup)

Record results in `state.md` under `## Environment`. Run the preflight before Spec, so a missing tool or a full disk is raised at the start of a run and does not stop it partway through.

1. **Disk:** `df -h /System/Volumes/Data`. A prebuild, a Debug build and a Release build together need about 10–15 GB. If less than 15 GB is free, stop and ask the user to free space. When the disk is full, subagents' shells fail (ENOSPC) and builds fail partway through.
2. **Tools:** `xcrun simctl help >/dev/null`, then `maestro --version`. If Maestro prints "Unable to locate a Java Runtime", try `JAVA_HOME=/opt/homebrew/opt/openjdk@17 maestro --version` (or `JAVA_HOME=$(/usr/libexec/java_home -v 17)`). If that works, record the exact `JAVA_HOME=…` prefix in `state.md` and include it in every Maestro command you give a subagent. If nothing works, ask the user to install Java 17+ now.
3. **Run simulators:** create this run's own devices so parallel runs never install over each other (every build uses bundle id `com.lambchomp.app`):

   ```bash
   xcrun simctl list devicetypes | grep -E "iPhone SE|Pro Max"
   xcrun simctl create "lc-<slug>-se" "iPhone SE (3rd generation)"
   xcrun simctl create "lc-<slug>-max" "<newest iPhone Pro Max device type>"
   xcrun simctl boot <se-udid>
   open -a Simulator
   ```

   Record both UDIDs. Never use, erase, or shut down a simulator this run did not create.

   **After every boot, wait and warm up before any Maestro run that counts.** Run `xcrun simctl bootstatus <udid> -b`, which returns once the simulator has finished booting. Then install the app and run one throwaway `maestro --device <udid> test .maestro/smoke.yaml` with output in the session scratchpad. Its result does not count. On a cold boot the first Maestro session also starts its XCTest driver, and in the field-one-swipe run that first query timed out after 100 s on the Pro Max even though the app was fully drawn. If a counted flow still fails with a driver timeout while its screenshot shows the app drawn, rerun that flow once and record both runs. A second failure is a real `FAIL`.

   **Only one simulator is booted at a time.** Boot only the SE at Setup and leave the Pro Max shut down. Each stage finishes its SE work, shuts the SE down (`xcrun simctl shutdown <se-udid>`), and only then boots the Pro Max. Both screen sizes are still covered, one after the other. Include this rule in every subagent prompt that touches a simulator.
4. **Metro port:** Debug builds load JS from Metro. Pick a free port from 8090–8199 (`lsof -nP -iTCP:<port> -sTCP:LISTEN`); 8081 belongs to the user. The orchestrator starts and stops Metro and records its PID. Subagents reuse it and never start another. Start it in the background from the worktree:

   ```bash
   env -u CI npx expo start --port <port> > .delivery/evidence/metro.log 2>&1
   ```

   Do **not** set `CI=1` to make it non-interactive: in CI mode Metro turns off its file watcher ("reloads are disabled"), so files created after it starts fail with "Unable to resolve". Check that it is serving with `lsof -nP -iTCP:<port> -sTCP:LISTEN -t`.
5. **Point the Debug app at the run's Metro port.** Without `expo-dev-client`, a Debug build ignores `--port` and the `__expo_url` deep link, and looks for Metro on 8081 ("No script URL provided"). Set the app's own default on each run simulator before its first Debug launch, and again if the app is uninstalled:

   ```bash
   xcrun simctl spawn <udid> defaults write com.lambchomp.app RCT_jsLocation "localhost:<port>"
   ```

   The setting survives `launchApp: { clearState: true }`. Release builds embed their bundle and ignore it.

## Builds

`/ios` is generated by prebuild and git-ignored. `npx expo run:ios` prebuilds if needed, compiles, installs, and launches.

- **While coding (Debug):** `npx expo run:ios --device <udid> --port <port>`, with the orchestrator's Metro already running and `RCT_jsLocation` set (preflight step 5). Do one build, then iterate through Metro reloads, not rebuilds.
- **Maestro against a Debug build:** write `--test-output-dir` (and any screenshots) under `.delivery/evidence/` or outside the worktree, never anywhere else in it. Metro watches the worktree, and a new file there can reload the app and reset the field mid-flow. `metro.config.js` blocks `.delivery/`, so Metro neither watches nor serves it. Release runs are not affected.
- **For Verify (Release):** after the code is committed, build without Metro or the dev overlay, which otherwise rebuilds mid-run and can show a red-box error:

  ```bash
  npx expo run:ios --configuration Release --device <se-udid> --no-bundler
  ```

  Later, after the SE is shut down and the Pro Max is booted, install the same `.app` on the Pro Max with `xcrun simctl install <max-udid> <path-to-.app>`. The build prints the path, under `ios/build/` or DerivedData (`Build/Products/Release-iphonesimulator/LambChomp.app`). Rebuild after every commit.

If the project later adds `expo-dev-client`, Debug launches open the dev launcher first; Maestro flows must then open the dev server URL. Release builds are unaffected.

## Required checks

Run from the worktree. Record every command with exit code. Work through one simulator at a time: do every SE check (steps 2–7, and the Perf Monitor check below if `ui` is flagged), shut the SE down, then boot the Pro Max, install the same `.app`, do the boot wait and warm-up from preflight step 3, and repeat steps 3–7 there.

1. `npm run gate`. Read `.delivery/gate.json`; each sub-gate (typecheck, lint, jest, levels, economy) gets its own status.
2. Release build, installed on each run simulator in turn. A build failure is `FAIL`.
3. Maestro, once per simulator (prefix with the `JAVA_HOME=…` from `state.md` if one is recorded):

   ```bash
   maestro --device <udid> test .maestro/ \
     --test-output-dir .delivery/evidence/maestro-<se|max> --format junit \
     --output .delivery/evidence/maestro-<se|max>.xml
   ```

   Flows use `takeScreenshot`; screenshots land in the test output directory. Use `--debug-output` on failure for logs and the view hierarchy.
4. Flow-specific checks for each AC. If a flow does not exist yet, write a run-only flow in `.delivery/flows/` (never in `.maestro/`, which is product code owned by the implementer).
5. Extra screenshots when needed: `xcrun simctl io <udid> screenshot .delivery/evidence/<ac-or-check>-<se|max>.png`.
6. Look at every screenshot. Check clipping, overlap, safe areas, unreadable text, and that the full paddock is visible on SE.
7. Crash and red-box check: `xcrun simctl spawn <udid> log show --last 5m --predicate 'process == "LambChomp"' --style compact | grep -iE "fatal|exception|crash"` (the process name comes from the generated Xcode project; confirm it in `ios/`). Any new crash is `FAIL`.

### Flag extras

- `save` upgrade check: in a base worktree, build `origin/main` in Release and install it; play a field (a Maestro flow is best); then `xcrun simctl install` the branch build over it without uninstalling, launch, and confirm stars and coins survived. Screenshot before and after.
- `native`: `npx expo-doctor`, `npx expo prebuild --clean`, then the build above. Revert any generated noise outside `/ios` and `/android`.
- `ui` swipe feel and 60fps: Perf Monitor in a Debug build for a frame-rate sanity check; feel on a physical device is `MANUAL` with exact steps.
  - **Who provides what:** the orchestrator keeps Metro running through Verify and gives the verifier its port and PID. The verifier never starts or stops Metro.
  - **When:** on the SE, after the Release checks and before shutting the SE down. Do one incremental Debug install (`npx expo run:ios --device <se-udid> --port <port>`; no `prebuild --clean`).
  - **How:** open the dev menu by sending a `devMenu` message to Metro's `/message` socket, turn on Show Perf Monitor, play the field's par solution, and screenshot after each swipe. Turn the Perf Monitor off afterwards. Record UI-thread and JS-thread fps.
  - A Perf Monitor reading taken before the commit under test cannot be `CARRIED`.

## Pre-existing failures

Before reporting a product failure, check `origin/main`. Ask the orchestrator for a base worktree: `git worktree add --detach ~/Projects/lamb-chomp-worktrees/<slug>-base origin/main` then `npm ci`.

- Fails the same way on base and the change does not make it worse: `PRE-EXISTING`.
- Absent on base, or worse on the branch: `FAIL`.
- Not compared: say so. `PRE-EXISTING` is never assumed.

## Re-verification after a fix

- Always rerun `npm run gate`, the Release build, and the full `.maestro/` suite on both simulators.
- Rerun targeted checks for changed files and every AC they can affect.
- Carry other results only if their code is unchanged: label `CARRIED (<sha>)`. Never carry across a change to covered code.

## Progress

Append a timestamped line under `## Progress` in `verify.md` as each step starts and ends.

## Reporting

Statuses: `PASS`, `FAIL`, `PRE-EXISTING`, `CARRIED`, `NOT RUN`, `MANUAL`. `MANUAL` is allowed only for physical-device feel or performance, Android, and App Store/TestFlight steps. A required check that did not run fails verification. Use `BLOCKED` overall when a tool or environment is missing and no product failure was found.

`verify.md` must contain these exact lines, each on its own line, which the PR hook reads:

```text
Overall: PASS
Commit: <full 40-character sha from git rev-parse HEAD>
```

`Overall:` is `PASS`, `FAIL`, or `BLOCKED`. The sha is the commit that was built and tested. If the tree was dirty when you started, stop and tell the orchestrator instead of verifying.
